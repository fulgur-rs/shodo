# `resolve_ch` / `resolve_ic` cost after PR #87

PR #87 made `ch` and `ic` use a shaped single-character advance to agree with layout's 1/64 px rounding. In the fixed ch-heavy caller workload below, the change increased warm unit-resolution time by **10.59×** and full layout time by **1.50×**. The layout path with unit values prepared in advance stayed near parity. This is a reproducible performance regression for this workload; it is not a WPT pass-rate or real raikiri page timing result. The precision correction remains necessary. A bounded, correctness-preserving reuse strategy is tracked in `shodo-6hd`.

The before version is `d0784ba6fdd0fa8964da3cc6b06cea7ec55f2a63`, the first parent of the [PR #87 merge](https://github.com/fulgur-rs/shodo/pull/87). The after version is its actual merge commit `35eda9ee7b4bd816041822aede2c913046d0ac05`. Comparing the branch HEAD directly would include unrelated differences from the then-current main; these two commits differ only in PR #87's three files.

The committed [ch_cost example](../../dev/bench/examples/ch_cost.rs) models 96 inline spans of `itemNNN 00 水 ` with alternating fixed Latin/CJK fixture families and 16, 18, 20, or 22 px font sizes. Each span resolves three `ch` values (start/end margins and letter spacing) and one `ic` value (start padding), for **288 `resolve_ch` and 96 `resolve_ic` calls** per document. It builds and breaks a paragraph in an 800 px viewport. `ch` and `ic` together are measured both alone (`units`) and inside `full_layout`; `layout_only` uses the same prepared values and builds/breaks without resolving units inside the operation. The separate `ch` and `ic` operations isolate each public method. Font loading, query/spec construction, and prepared values are outside the measured scopes.

Both versions used the same example source SHA-256 `d38beec6f07f1215cfafe62249a2e0c42bc4532c237647e0331379a4afb372c1`, the same committed `Cargo.lock` hash, the same fixture-font bytes, `cargo build --offline --release` at Cargo's default release opt level, Rust 1.96.0, and an AMD Ryzen 5 5600G on Linux. Time and allocation builds used separate target directories for each version. Every process was pinned to logical CPU 0; each pair alternated which version ran first. Each operation had 32 warmups. Time: 12 independent process pairs, 21 samples of 8 repetitions per process; the table uses each process's median, then the median of paired after/before ratios. Allocation: 5 independent process pairs, 21 single-operation samples per process, with a separate `allocation-counting` build. Allocation calls and bytes are requested allocator operations, not RSS. All raw samples, process order, exact hashes, build details, and the per-pair medians are retained in [compressed raw data](data/ch-unit-cost-raw.json.gz), [summary](data/ch-unit-cost-summary.json), and [manifest](data/ch-unit-cost-manifest.json). The raw gzip SHA-256 is `c357d27cf82cbe780aad861db23513547688c119f723224f08325e7c5c86e061`.

Both versions produced 20 lines. The sum of line inline widths was 14,891.671875 px before and 14,892.046875 px after; the 0.375 px difference is consistent with the rounding correction, but the measurement does not establish full glyph/geometry identity. This stress input is intentionally dense in `ch`; its 50% end-to-end increase must not be extrapolated to ordinary pages or used to judge the saved S4 spikes. The isolated unit cost and unchanged allocation count for `layout_only` locate the main extra work in repeated unit resolution, rather than paragraph layout itself.

To rerun, check out the two commits separately, copy the same example source into both, build `cargo build --offline --release -p shodo-bench --example ch_cost`, then build again with `--features allocation-counting`. Run the binaries with `time` and `alloc` respectively. The manifest records source/font/lock/binary hashes; the JSON files preserve all observed values so the aggregate can be independently recalculated. No saved S4 spike branch or WPT baseline was changed.
